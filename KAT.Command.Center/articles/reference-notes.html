Reference Notes

Detailed implementation-facing notes that are useful when a workflow behaves unexpectedly, but are not needed for normal use.

Work item state transitions

State accepts Active, Closed, Proposed, and Resolved. Blank or unchanged State creates no State update. In a Close Task dialog this fails validation, even with a comment entered.

  • Bug: Proposed to Active or Closed; Active to Proposed or Resolved; Resolved to Active or Closed; Closed to Active.
  • Task: Proposed to Active or Closed; Active to Proposed, Resolved, or Closed; Resolved to Active or Closed; Closed to Active or Proposed.
  • Feature: Proposed to Active, Closed, or Resolved; Active to Proposed, Resolved, or Closed; Resolved to Active or Closed; Closed to Active.
  • Requirement: Proposed to Active, Closed, or Resolved; Active to Proposed, Resolved, or Closed; Resolved to Active or Closed; Closed to Active.

Feature and Requirement's Proposed to Resolved transition passed validation but is not advertised in TFS metadata. Other transitions follow the type metadata; individual item rules may still reject a change. No intermediate saves are attempted after arbitrary errors.

Choosing Closed for an Active Bug automatically saves Resolved, then Closed, in any comment-modal variant. Comment, reassignment, and Triage go only in the final save. These are two revisions, not an atomic update. If closing fails, the modal stays open with your inputs retained and the last confirmed State updates to Resolved. Retry skips that already-completed transition. A timeout may mean the final save landed without confirmation; check TFS before retrying if the outcome is uncertain. State changes guard against a changed State or type on the server and are not automatically retried.

Closing a Proposed item sets its Reason to Rejected. TFS chooses the Reason; the dialog does not override it. For a Task, Active to Closed means Complete and Does Not Require Review/Test; Resolved to Closed means Review/Test Passed.

Recognizing probable hotfixes

A direct upload to the upper CalcEngine can introduce versions that do not exist in lower history. A warning triangle marks these as probable patches.

  1. If PROD is already in lower history but UAT is missing, fetch upper history between those two environment versions. Add upper-only versions with patch warnings.
  2. If the lowest upper version is missing and is older than the oldest lower result, look back one decimal increment in lower history. For example, an oldest result of 1.1636 means a lookup from 1.1635 through 1.1636. Take the nearest strictly older lower version; use it as the baseline only if it is below the lowest upper version.
  3. Fetch upper history from that baseline (or the lowest upper version if no baseline was found) through the oldest lower result, extending the upper end when needed to include UAT/PROD. Merge newest first, keeping lower's entry when the same version appears in both histories. The confirmed lower baseline is not a patch.

If lower history is empty, fetch the known UAT/PROD range and mark its rows as probable patches. With only one populated upper environment, that fallback requests its single version. The lookup makes at most three history requests; a failed request is shown as an error, not as an empty result.

This is a version-number heuristic, not a file-content comparison. A hotfix that reuses a lower version number cannot be distinguished; older upper-only changes are not searched when the current upper versions already exist in lower history. The backward lookup checks one decimal increment only, so skipped numbers or unusual numbering can leave the baseline undiscovered. Such cases retain the known upper minimum rather than guessing an older baseline.
