Release Pipeline

Use this card to understand each release environment, approve pending gates, redeploy canceled stages, queue a build, and remove stale releases through a reviewed cleanup plan.

How to read pipeline

Table context
Each release is a row. Named environments appear together in the Environments column; cleanup state and ad-hoc delete are separate columns showing actions when applicable.
Build rows
Above the newest release, tinted and edged in their own colour, sit any builds newer than it that are still running or that failed. Successful builds are not listed - once one becomes a release it appears as a release row instead. Only builds of the pipeline's release branch count, so a failed feature-branch build never shows here. Queueing a build adds its row immediately. These rows carry no actions: use the build number to open the build in TFS.
Build chips
A build uses the same chips as a release environment - same icons, same colours - and sits in the lowest environment's column, because a build comes before any stage can deploy. So a running build wears the same blue spinner as a running deployment directly beneath it. Hover for the build's state and who queued it.
Hover details
Hover an environment chip to see its state, who triggered, approved, or rejected it and when.

Notable Features

  1. View and manage all active releases for a Site or Api
  2. Queue new builds; on success, triggers a new release generation
  3. Hover over environment chips to see their state, who triggered, approved, or rejected it and when each environment state occurred
  4. Stale release cleanup; automatically removes outdated releases to keep the pipeline clean
  5. Delete completed and covered (a newer release deployment deployed to all the same environments) releases manually

From and To Detection

From and To are automatically detected based on the following rules.
  1. Sort all active releases newest-first: [15, 14, 13, 10]
  2. Resolve To - scan from index 0 for the first release where every PROD environment succeeded
  3. If To resolved at index > 0, From is index - 1 (the next newer release)
  4. If To resolved at index = 0 (the newest release is itself already PROD-complete), there's nothing newer to be From. Slide-back check is applied:
    - From is index 0
    - To is ProdIndexFrom(1) - scan from index 1 for the next PROD-complete release (note that any releases that are not complete - failed, cancelled, etc. - are skipped until next PROD is found)

Given above sample, Release 10 is the last, most recent release that every environment is complete. Release 13 would be the first available release after even though it has a canceled PROD environment it is still eligible to redeploy.

Enter explicit release numbers in the Application Bar filter row when you need a specific comparison. An invalid number makes the Release Pipeline and Release Differences unavailable until corrected.

Comparison UnavailableThe following cases can result in a grey Nothing to compare or amber Unavailable state: no PROD-complete release yet (brand new pipeline) or only a single PROD-complete release with nothing to compare against.

Determining Cleanup Eligibility

The following eligibility rules apply for cleanup in order:

  1. Newest release (Anchor) is never touched.
  2. Releases where every environment was successfully deployed are never touched (can use Ad Hoc Delete).
  3. Releases covered by any newer release are marked as CANCEL + DELETE. Covered means all a newer release has exactly matching environment(s) deployed or is fully complete (meant to handle renames like PROD -> PROD Group 1/PROD Group 2).
  4. Releases where a newer release exists, but the release is not covered are marked as CANCEL . Active environments are canceled with the assumption that a newer release will eventually be the production release candidate; the release is not deleted since it is only assumption and not fact. Canceled environments can always be redeployed.
  5. Two further rules limit what you may do, as opposed to what the pipeline allows. A stage waiting on an approval you are not an approver for is never cancelled - cancelling it ends the release's run at that gate, which is the approver's decision. And a release cannot be deleted, by cleanup or by Ad Hoc Delete, if it published to any environment you have no approval authority over. Authority comes from the release definition's approver roster for that environment, plus the definition owner's override; environments whose gate is automated (typically DEV) are exempt, as are environments this release never reached. Where a release carries an environment the definition no longer has - an old PROD against today's PROD Group 1 - there is no roster to read, and only the person who actually approved that stage qualifies.

Blocked, failed, and retry cleanup states

All PATCH (cancel) calls run concurrently first. Only if every cancel succeeds does it proceed to the DELETE calls.

Rendering Meaning Next move
BLOCKED The cleanup planner found a reason not to act. Click the chip to see why. Typically a newer release has not yet deployed to matching environments; once it does, the block clears on the next refresh.
DONE The cancel or delete call succeeded. No action needed.
FAILED A cancel or delete call returned an error. Click the chip to see the error detail. Resolve the issue in TFS, then re-run cleanup.
SKIPPED A cancel call failed, so dependent delete calls were not attempted. Resolve the failed cancel first (click its chip for detail), then re-run cleanup.
