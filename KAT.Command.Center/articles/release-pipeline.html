Releases · Pipeline

Use this page to understand each release environment, approve pending gates, redeploy canceled stages, queue a build, remove stale releases through a reviewed cleanup plan, and compare the commits between two releases.

The page lists the site's builds and releases first, then the From and To release cards, then the commits between those two releases. Open it from the Releases group in the rail, or click the Releases · Pipeline tile on the Dashboard.

Sample Pipeline

Notable Features

  1. View and manage all active releases for a Site or API
  2. Queue new builds; on success, triggers a new release generation
  3. Hover over environment chips to see their state, who triggered, approved, or rejected it and when each environment state occurred
  4. Stale release cleanup; automatically removes outdated, unfinished releases to keep the pipeline clean or manually delete completed and covered releases
  5. See the commits each release carries; see Release Differences
  6. Watch the rail badge for approvals you can make, uncovered failed stages, and failed builds; see Rail badges and What's Happening for the cross-page rules.
  7. After an approval, redeploy, queued build or cleanup, and while anything is still in flight, the page keeps itself current: the Pipeline rail entry shows three animated dots while it is watching.

From and To Detection

From and To are automatically detected based on the following rules.
  1. Sort all active releases newest-first: [15, 14, 13, 10]
  2. Resolve To - scan from index 0 for the first release where every PROD environment succeeded
  3. If To resolved at index > 0, From is index - 1 (the next newer release)
  4. If To resolved at index = 0 (the newest release is itself already PROD-complete), there's nothing newer to be From. Slide-back check is applied:
    - From is index 0
    - To is ProdIndexFrom(1) - scan from index 1 for the next PROD-complete release (note that any releases that are not complete - failed, cancelled, etc. - are skipped until next PROD is found)

Given above sample, Release 10 is the last, most recent release that every environment is complete. Release 13 would be the first available release after even though it has a canceled PROD environment it is still eligible to redeploy.

Choose explicit releases with the From and To pickers in the page head when you need a specific comparison. Each entry shows the release number and the environment it has reached. From must be newer than To: a valid pair applies at once, and your choice lasts until you change site or close the window. While the Pipeline page is open, Alt+F and Alt+T open those pickers; hold Alt to see the underlined letters.

If you pick a From that is not newer than To, the page keeps showing the previous comparison, marks the pickers, and holds Pipeline refreshes until you fix the pair or click Restore comparison.

If a chosen release cannot be resolved, the page shows an amber warning with the range pickers still available so you can choose an active release.

Comparison UnavailableThe following cases can result in a grey Nothing to compare or amber Unavailable state: no PROD-complete release yet (brand new pipeline) or only a single PROD-complete release with nothing to compare against.

Determining Cleanup Eligibility

The following eligibility rules apply for cleanup in order:

  1. Newest release (Anchor) is never touched.
  2. Releases where every environment was successfully deployed are never touched (can use Ad Hoc Delete).
  3. Releases covered by any newer release are marked as Cancel + Delete. Covered means all a newer release has exactly matching environment(s) deployed or is fully complete (meant to handle renames like PROD -> PROD Group 1/PROD Group 2).
  4. Releases where a newer release exists, but the release is not covered are marked as Cancel . Active environments are canceled with the assumption that a newer release will eventually be the production release candidate; the release is not deleted since it is only assumption and not fact. Canceled environments can always be redeployed.
  5. Two further rules limit what you may do, as opposed to what the pipeline allows. A stage waiting on an approval you are not an approver for is never cancelled - cancelling it ends the release's run at that gate, which is the approver's decision. And a release cannot be deleted, by cleanup or by Ad Hoc Delete, if it published to any environment you have no approval authority over. Authority comes from the release definition's approver roster for that environment, plus the definition owner's override; environments whose gate is automated (typically DEV) are exempt, as are environments this release never reached. Where a release carries an environment the definition no longer has - an old PROD against today's PROD Group 1 - there is no roster to read, and only the person who actually approved that stage qualifies.

Cleanup Confirmation

IrreversibleCleanup can cancel environments and delete releases. Review every planned API call before continuing.

Blocked, failed, and retry cleanup states

The cancel calls run first, a few at a time. A delete runs only once every cancel has succeeded; if any cancel fails, no release is deleted. The dialog shows each call's status as it finishes. A call that takes longer than ten seconds is reported as failed, but TFS may still have completed it, so refresh and review the new plan before running cleanup again.

Rendering Meaning Next move
BLOCKED The cleanup planner found a reason not to act. Click the chip to see why. Typically a newer release has not yet deployed to matching environments; once it does, the block clears on the next refresh.
DONE The cancel or delete call succeeded. No action needed.
FAILED A cancel or delete call returned an error. The error shows beneath the call. Resolve the issue in TFS, then re-run cleanup.
SKIPPED A cancel call failed, so no delete calls were attempted. Resolve the failed cancel first, then re-run cleanup.

Release Differences

Below the release cards, the page lists every commit between the To release and the From release, grouped by repository. The sample below has Show Pending turned on, so work newer than From is listed above it, one group per origin, newest first: Needs build for commits newer than the latest successful build, New for commits that are built but not yet in any release, and one group per release newer than From. With Show Pending off, only the commits between To and From are shown.

Notable Features

  1. See commits across all repositories required to build the site or API to be included in the current release (not just commits isolated to the site or API repository)
  2. Uses the same From and To as the rest of the page; see From and To Detection.
  3. Show Pending in the page head appears when there is pending work. It shows release candidates newer than the current From release and commits that have not been published yet; click it again (Hide Pending) to return to the plain comparison.
  4. View any commit on TFS via the commit hash link.
  5. Open an associated work item via the #work-item reference in a commit comment.
  6. Read the complete commit comment with the details button when the comment has more lines or is cut off.
  7. Collapse anything you have finished with: the chevron on a repository header folds that repository's commits away, and with Show Pending on, the chevron on a release group folds the whole release. Headers stay put while you scroll.
  8. Click a repository on the Dashboard's Releases · Pipeline tile to jump straight to its commits here.
  9. Commits waiting for a build are also surfaced in What's Happening.
