Tools · local Git

Repository Status

Repository Status watches your local Git repositories in the background.

Repository Status, under Tools in the app rail, watches the local Git repositories found under the roots set on the Repository Status page in Settings. Changing site never resets its results, filters or notices. Monitoring starts when the app opens, without delaying the dashboard, and carries on while you are on other pages or the window is minimized. Apart from fetching, it only reads until you ask it to act: Pull, Sync, Commit and Push run only on the rows you choose. Pull and Sync run a plain git pull, so your own Git configuration decides between fast-forward, merge and rebase, and a conflict is left for you to resolve; a force push never replaces a remote branch that changed after you reviewed it. Worktree cleanup is the only thing that removes a worktree, and only one you ticked in the table.

What is checked, and when

  • Local status, every 2 minutes by default: each checkout's branch, its incoming and outgoing commits against its upstream, and its added, modified, deleted, untracked and conflicted files, in the working tree and staged. Reading status never takes Git's index lock, so it cannot get in the way of your own Git commands.
  • Fetch, every 30 minutes by default: git fetch of the upstream remote of each checked-out branch, once per repository even when several of its worktrees track that remote, eight at a time. Fetching starts only after local status is on screen. It updates remote-tracking branches and so the incoming counts, pruning those whose remote branch was deleted; it never pulls, checks out or edits files. Git is never allowed to prompt, so a remote that needs you to sign in fails and is reported instead of waiting.
  • Opening the page: when the selected site's Release Pipeline has loaded and no check or fetch is running, opening Repository Status first checks and fetches the repositories that pipeline builds, then restarts both timers. A repository counts as one of them when a remote URL ends in /_git/ and its name, or failing that when its folder has the name. If none matches, nothing extra runs.
  • Either timer can be turned off in Settings; F5 keeps working. A check still running when its timer comes round is skipped rather than queued, so a slow network never builds a backlog.

The header shows how many repositories, and (when there are any) linked worktrees, are monitored, when local status was last checked and when a fetch last succeeded. Background checks pulse the rail entry the way other refreshes do.

Finding repositories

Each root is scanned for Git repositories, nested ones included. Linked worktrees are found through Git and listed under their repository, even when they live outside the roots. Submodules are not listed on their own, symbolic links and junctions are not followed, and a folder that matches an ignore pattern is skipped with everything under it.

The list found is saved under %LocalAppData%\KAT.Command.Center, so the next start checks status straight away without scanning the roots again. Timed checks and fetches use that saved list; a repository cloned since then appears after F5. Changing the roots or ignore patterns rescans when you save Settings; other settings, including the order of the roots, do not. If a root is missing or cannot be read, the page and What's Happening say so, the other roots carry on, and repositories found there before stay listed as unavailable rather than disappearing. A saved list that cannot be read is reported, and the roots are scanned again.

Refreshing

F5 or the ↻ button rescans the roots and checks the local status of every repository. It does not fetch. Use Ctrl+F5 or Ctrl+Click the refresh icon to fetch all known repositories now, even when scheduled fetching is off; this restarts the fetch interval. Fetch failures appear in the header in the repository warning color beside the last successful fetch time; the refresh icon's color and tooltip stay unchanged. While a scan or check runs, Cancel stops it and the previous results stay.

When filters hide repositories, the column header reads, for example, Repository (12 of 119 shown). Under the filters are reasons as chips, each shown only when at least one listed checkout has it: the informational ones (no upstream, detached HEAD, no commits yet) first and plain, then problems by count, a failed fetch in orange and the rest in red. Press a chip to narrow the current Show view, root and path filter to the repositories with that reason; press it again, or change a filter, to go back. The selected chip has a stronger border in its own color; the other chips are muted. Timings and progress are kept for the Diagnostics page rather than the status line.

Reading the table

Repositories are listed by the root they were found under, in the order of the roots in Settings (a repository under nested roots goes with the longest one), then by name. Each row shows:

  • Repository: the folder name, the … actions button, a worktree chip with the number of linked worktrees, and the parent folder in grey. The parent folder gives way first when the column is narrow. A name in orange means its last fetch failed or it has merge conflicts; in red, its upstream branch is gone or the checkout could not be read. Point at the name or icon to read the error, such as Git's own authentication message; Needs an elevated terminal is added when Git was refused permission.
  • Branch: the checked-out branch ((detached) for a detached HEAD, bare for a repository without a primary checkout). Point at it for its upstream.
  • Commits: ↓ incoming and ↑ outgoing commits, empty when level with the upstream, a grey NA chip when the branch has no upstream and — when the counts are unknown (detached, no commits yet, upstream gone). After a failed fetch the counts are the last known ones, in italics. When Pull or Push is available, the count is a button for it: ↓ pulls, ↑ pushes.
  • Status: empty when clean, otherwise one chip with the working tree on the left (+ added, ~ modified, - deleted, ? untracked) and what is staged on the right (+ ~ -); a side with nothing in it is left out, a rename counts as modified, and conflicts lead in red as !. Point at the chip for the counts in words.

Expand a repository (click it, or press Enter or →) to see its other branches and its linked worktrees, each worktree with its own branch, status and actions button. Background checks update rows in place, so what you expanded, where you were scrolled and the row you focused stay put. On a narrow window the table scrolls sideways inside its card.

Filters

Missing root folders are reported in the page's warning callout, without repeating a count beside the problem chips.

The filters under the header only change what is shown; every repository is still monitored. They are remembered between sessions.

The Show list starts with All, Needs Attention, and Has Warnings. When more than one root is configured, a separator precedes the roots in Settings order; a single root is omitted because All covers it. Count badges are hidden when zero.

  • Path filter keeps repositories whose folder, or any worktree's folder, contains the text.
  • Show: a root's own entry, {name} Repos, lists everything under that root (each root can be named in Settings; without a name the folder name is used). The three views are Needs Attention (the default) lists repositories with uncommitted changes, incoming or outgoing commits, an unfinished Git operation, an unreadable checkout or a gone upstream; it also includes repositories with other local branches, with a linked worktree that needs attention, or with any linked worktree while clean worktrees are shown. Remote branches alone do not count. All lists everything; Has Warnings lists repositories whose last fetch failed. A failed fetch never moves a repository into or out of Needs Attention: it only colours its row orange wherever it appears. Each entry shows how many repositories it lists, before the path filter narrows them. Needs Attention turns red with a red dot when a repository it lists has an error (an unreadable checkout or a gone upstream), or orange with an orange dot when one has a warning; Has Warnings turns orange with an orange dot while it lists anything. A dot on the corner of the closed list says the same whichever entry is chosen: red when Needs Attention has an error, otherwise orange when there is a warning, so a problem is visible from any view.
  • Branch detail: None, Local (the default) or Local + remote branches in each repository's expansion. Changing it immediately shows the selected details from the last status check, without running Git. Background checks and fetches refresh the branch list.
  • Show clean worktrees hides or shows linked worktrees that have nothing needing attention. A worktree with uncommitted changes, incoming or outgoing commits, an unfinished Git operation, an unreadable checkout or a gone upstream is always listed, whichever way the switch is set, and still pulls its repository into Needs Attention. With it off, the normal worktree chip remains while any worktree needing attention is listed, a repository whose only worktrees are clean no longer expands, the status line counts repositories and the worktrees still listed, and the Clean Worktrees batch action remains available while any worktree row is listed.

A row an action worked on stays on screen when it finishes, even if the filter would now hide it, with a small × (Move to filter) at the far right of the row that hands it back to the filter. Those rows return to the filter when you change a filter, press a chip, refresh, or leave the page.

What's Happening

Incoming commits appear on the Dashboard's What's Happening list. Up to four repositories each get a row naming the branch and how many commits it is behind; five or more fold into one row. A repository counts once however many of its worktrees are behind. Rows update after each fetch and leave once the checkout has caught up. A repository's row opens Repository Status focused on it, kept on screen whatever the filters say; the grouped row opens an Incoming commits view, shown as a pressed chip in the status line, which is not saved and closes when you press the chip. A root that cannot be read stays listed until it can. A repository with unresolved merge conflicts gets a row too, which opens the repository the same way; the rail badge counts these rows as well.

A repository's row has a Pull button that acts exactly like the table's: it pulls the repository's behind checkouts that can be pulled, and its tooltip says why when none can (a dirty or diverged checkout still reports its incoming commits). The grouped row has Pull all eligible, which opens a preview of every checkout that is behind, each with its upstream; the clean ones are checked and the rest are listed, disabled, with the reason. The preview is the Pull confirmation, so with Confirm Pull off it is skipped and every checkout it would have checked is pulled. While it runs, the header's Cancel stops it.

Row actions

A failed Fetch stays a warning. An explicit Fetch action shows one dismissible inline warning with the full action error and, when applicable, the stale-count note. Background fetch failures use the warning-colored name and icon, filter chip and hover explanation without an inline result.

Every checkout row has a … button that opens its actions. An action with nothing to do is left out (Push when nothing is outgoing); one that would do something but cannot right now is shown disabled, with the reason in grey under it (Pull with uncommitted changes). Every item has an icon:

Git actions come first, with Show Differences then Commit… when applicable. After a separator come Force Push… when offered and the terminal actions; another separator precedes additional remotes.

  • Commit…: see Commit. Offered when there are changes; disabled on a detached HEAD or with conflicts.
  • Open Terminal: a new tab, titled with the folder name, in your most recent Windows Terminal window, in the checkout's folder; or PowerShell (pwsh, then Windows PowerShell) when Windows Terminal is not installed.
  • Open Terminal (Administrator): the same, run as administrator, so Windows asks for permission first; declining simply cancels. An elevated terminal cannot join your existing window, so it opens a new one. It needs Windows Terminal or PowerShell 7.
  • Show Differences: offered when there are changes. Opens the terminal and runs git difftool HEAD with your configured tool, which shows staged and unstaged changes to tracked files. It needs diff.tool to be set (for example git config --global diff.tool vscode); otherwise the app says so instead of opening anything. Untracked files have no committed version to compare.
  • Fetch: fetches origin; offered only when the branch has an upstream (the origin entry below fetches regardless). It never pulls, checks out or edits a file, and a failed fetch keeps the last counts and marks them stale.
  • Pull, Push and Sync: see Pull, Push and Sync.
  • Force Push…, in red: see Force Push.
  • One entry per remote other than origin, opening Fetch, Push and Force Push… for that remote.

Arrow keys move through the menu, → opens a remote's entries and ← closes them, Enter chooses, and Esc closes the menu and returns focus to the … button; ↓ on the button opens it. Scrolling or resizing the window closes it. If Git or a terminal cannot be found, the notice bar says what is missing. Nothing you type, and no branch or path name, is ever run as a shell command: each is passed to the program as a single argument.

When an action succeeds, its row simply updates. When it fails, is refused or may not have finished, the row expands with a tinted background and border. The message wraps below the repository details, aligned with its name, with inline × Dismiss and Open Terminal links when applicable (and Retry push for a failed push). Problems found by polling or F5, including unavailable checkouts and gone upstreams, use filter chips, name and icon colors, and hover explanations instead of dismissible inline messages. Dismissing an action result does not clear an underlying checkout problem. Page warnings share one callout, and page errors share another.

Pull

Pull runs a plain git pull with no options of its own, so your Git configuration (pull.rebase, pull.ff, branch.<name>.rebase) decides whether it fast-forwards, merges or rebases. A merge never opens an editor for its message. A checkout can be pulled when it is on a branch with a remote upstream and has no staged, unstaged, deleted, renamed or conflicted files; untracked files alone do not block it, and neither does having commits of your own, so a diverged checkout can be pulled without pushing. It runs, under that repository's lock:

  1. read the checkout again and refuse it if the branch or HEAD is not what the row showed, or if it is now dirty, detached, has no upstream or its upstream is gone;
  2. git fetch of its upstream remote;
  3. read it again, and report already up to date if nothing is incoming;
  4. git pull.

A refusal names the reason (uncommitted changes, no upstream, detached HEAD, upstream gone, branch or HEAD changed); a failure shows Git's own message, for example when diverged branches need pull.rebase or pull.ff set. One case to know: if the incoming commits add a file that also exists untracked in your folder, Git refuses to overwrite it, and the row reports that failure. A Git call that times out is reported as may not have finished, not as a clean failure, and is never retried automatically.

Conflicts

Conflicts and unfinished operations use the warning-colored repository name, Status indicator and Conflicts filter chip, without an additional inline warning callout. Details remain available on hover; a separate failed action still reports its error.

When a pull, merge or rebase leaves files in conflict, or any merge, rebase, cherry-pick or revert is still unfinished in the checkout (even after you have staged every resolved file), nothing is aborted for you. The repository name turns orange, its hover describes the conflict or operation, and What's Happening lists the repository (it also counts on the rail badge and is listed under Needs Attention). Commit, Fetch, Pull, Push and Sync may be disabled while the operation is unfinished, and incoming/outgoing counts stop being buttons. Show Differences and the terminal actions remain available; Force Push and additional-remote push actions are not offered. Resolve the conflicts first using your preferred Git tool, such as VS Code, then finish or abort the merge or rebase. The row returns to normal at the next check, once Git no longer has the operation open.

Sync

Sync is offered only for a clean checkout that has diverged from its upstream (commits on both sides). It is Pull followed by Push, and runs under the repository's lock:

  1. read the checkout again and refuse it, like Pull, if its branch or HEAD changed or it is now dirty, detached or without a remote upstream;
  2. a plain git pull, so your Git configuration decides between merging and rebasing;
  3. push the branch to its upstream branch.

If the pull stops on a conflict, nothing is aborted and nothing is pushed: the checkout is left as Git left it so you can resolve it, and the row is marked as in conflict. If the pull fails for any other reason nothing is pushed either. If the pull succeeds but the push does not, the row says the branch was pulled and why the push failed. Use Pull instead when you want the upstream's commits but not to push yours yet.

Commit

Commit takes every change in the checkout: edits, deletions, renames and untracked files, exactly as git add -A followed by a commit would. Ignored files stay out. It always opens a review, because that is where you write the message; one message is used for every checkout in a batch, and it reaches Git on its standard input, so quotes, a leading dash or several paragraphs are committed as typed. Ctrl+Enter in the message box confirms. Cancelling the review, including with Esc, discards the message; the next review starts empty.

The review lists each checkout's changed files (the first 200, with the total). It runs, under the repository's lock:

  1. read the checkout again and refuse it if its branch or HEAD is not what the row showed, or it now has conflicts or a detached HEAD;
  2. git add -A, then git commit with your message. Your hooks run as they always do; nothing is skipped.

Nothing left to commit (for example, only ignored files had changed) is not a failure. A hook that rejects the commit, or a signing prompt that is not answered, fails that checkout with Git's own message and leaves the others alone. Note that the files are already staged by then.

Push and push targets

Push sends the checked-out branch to the branch of the same name on origin, always naming both sides (refs/heads/main:refs/heads/main), so your push.default setting never changes where it goes. If the branch has no upstream yet, it gets origin's same-named branch as its upstream. An existing upstream is never changed, even one that points somewhere else. Only the checked-out branch is pushed, never the repository's other branches, and a linked worktree is simply another checked-out branch, so pushing from one pushes that worktree's branch. Push is left out of the menu when nothing is outgoing and for a diverged checkout, which needs Pull, Sync or a force push.

Each remote other than origin has its own entry in the menu with Push and Force Push…. Pushing to a remote other than origin never sets or changes the branch's upstream. With no origin, only those entries are offered. With Confirm Push on, you are asked once, for example Are you sure you want to push 3 repositories?. A push that fails, for example because the remote has commits the branch lacks, offers Retry push.

Force Push

Force Push replaces the remote branch with yours, but only with a lease: when the review opens, the app asks the remote itself what its branch points at (or that it does not exist), and the push is sent with --force-with-lease naming exactly that commit. If anyone pushed to that branch after the review, or created it when it did not exist, Git refuses the push and the row says remote changed since review; nothing is retried. Because the expected commit is read from the remote at review time and not from your remote-tracking branches, a background fetch in between cannot quietly make the lease agree with the new remote state. A plain --force is never used.

A force push always opens its review and has no setting to switch that off: for each checkout it shows the remote, the branch, the commit expected on the remote (or absent) and your local commit. If the remote cannot be reached when the review opens, that checkout is left out and says why.

Batch actions

Each batch action is disabled when no row the current filters list qualifies for it, even if that row is inside a collapsed repository.

The Batch Action button in the page header acts on several rows at once. Its ▾ lists Pull Clean (checkouts that can be pulled), Push Commits (checkouts with outgoing commits that can be pushed to origin), Commit Changes (checkouts with changes that can be committed) and Clean Worktrees (linked worktree rows; hidden when no worktree row is listed). Once you choose one, the button repeats it for the rest of the session; until then it opens the list. It is disabled when no row qualifies for any of them.

Choosing one disables the button and adds a row at the bottom of the page header with Pull Clean:, an All box that ticks or clears every applicable row on screen, how many are ticked, Continue and Cancel. A checkbox appears on each row the action applies to. Continue runs the action on the ticked rows through the same confirmation a single row gets (the commit review, the worktree cleanup review of exactly the worktrees you ticked). Dismissing that confirmation keeps you in batch mode so you can change what is ticked. Cancel or Esc leaves without doing anything. While the action runs, the ticks are locked, the row reads Processing 3 of 8…, and Cancel stops the run; batch mode ends and the button comes back when the run does.

Choosing an action expands every repository holding a worktree it applies to. A repository's own checkbox only ever means its own checkout. When any of its worktrees qualify, a checkbox also appears beside the worktree icon in its count chip; it ticks or clears all of those worktrees at once and shows a dash while only some are ticked. Clean Worktrees ticks worktrees, never repositories, so there only the chip checkbox appears on a repository row.

Cleaning up worktrees

The Clean Worktrees batch action removes the worktrees you ticked in the table. A single worktree's … menu has Clean Worktree… for just that one, and a repository's menu has Clean Worktrees… for all of its linked worktrees, missing ones included. Nothing is pruned or removed until you confirm, and a timer, Fetch or F5 never prunes or removes anything. The review opens at once from the last status check, which also records each linked worktree's lock and whether its branch is merged into main; it runs no Git when it opens, so anything that changed since that check is caught when the cleanup runs (below). The review that follows lists each worktree once, as one of:

  • Missing worktree registrations: worktrees Git still lists but whose folder is gone. Their row's menu offers only Prune Worktree…. Each is pruned on its own (git worktree remove on just that path), so other missing registrations in the repository are left alone. It runs only while Git still lists that registration as missing; otherwise it is refused and you open the review again. The branch is kept.
  • Linked worktrees: each is either a plain removal or a forced one. A plain removal is a worktree that is unlocked, has nothing uncommitted (untracked files count) and has a reason to go: its branch is merged into the local main branch, or its upstream branch is confirmed deleted. Anything else is a forced removal, shown with a warning border and background and what makes it forced. The primary checkout, a worktree Git no longer lists and a checkout that could not be read cannot be removed at all; they are listed as blocked and are not acted on.

"Merged into main" means the branch is reachable from the local main branch; with no local main, only the deleted-upstream reason can apply. A branch created from main that has no commits of its own counts as merged, and the review says same commit as main so you can tell. A detached HEAD has no branch to check, so it is a forced removal.

An upstream counts as deleted from the last fetch: fetches prune, so a branch deleted on the remote loses its remote-tracking branch, and the review shows it as a plain removal without contacting the remote. Use Ctrl+F5 to fetch first if the remote changed recently. When you confirm, the review stays open with its buttons disabled while each such upstream is checked with the remote itself (git ls-remote --exit-code for the exact branch the local branch tracks); only a definite not found counts. A branch that is back, an authentication error, a timeout or an unreachable network refuses that worktree on its own row, and the rest run.

Before each removal the app checks everything again under the repository's lock: the worktree is still listed, is not the primary checkout, its folder is still there, and its branch and HEAD are the ones you saw. A worktree that moved on since the review is refused on its own row, forced or not. Without force it must also still be unlocked and clean and still have its reason; with force those three are waived and Git is given --force (twice for a locked worktree). Git's own refusals (for example a worktree with submodules) are reported as failures. The branch is never deleted: it stays in the repository with its commits. The rows then update to match.

The review is read-only: everything it lists that is not blocked is acted on, so change what you want by cancelling and re-ticking the table. It opens whenever Confirm worktree cleanup is on (the default), anything is forced, a prune is involved or something is blocked; otherwise the plain removals you ticked just run. Each row reads repository/branch (worktree folder), without the branch when HEAD is detached, with a chip saying what happens to it: Prune, Remove, Forced or Blocked. The Don't ask me to confirm worktree cleanup switch is offered only when nothing is forced, takes effect only if you confirm, and Settings turns it back on. A forced removal always asks, even with that setting off. Forced removals and prunes are each called out in the warning at the top of the review.

Confirmation, running actions and cancelling

Commit, Push, Pull, Sync and worktree cleanup each have their own confirmation, all on by default. Pull, Push and Sync ask one question, naming the repository or how many there are, for example Are you sure you want to pull 4 repositories?. Its Don't ask me switch takes effect only if you confirm; Cancel leaves the setting alone, and Settings can turn the prompt back on. Commit keeps its review, and a force push always shows its lease review. The grouped Pull all eligible preview is the confirmation when it is on, so you are not asked twice. Turning confirmation off never skips the checks above: the branch and HEAD comparison, the clean rules and the lease always apply. Each prompt is tied to the request that opened it, so an old prompt cannot confirm a newer one.

Actions on different rows can run at the same time: you can commit one repository while a batch pulls others. The rows an action is working on are dimmed, show moving dots after their folder, and take no new action until it finishes; asking for one there is refused. Only one batch runs at a time. Rows run four at a time; checkouts of different repositories run together and worktrees of one repository one after another, because they share Git's state. Refresh waits until every action has finished.

Cancel lets the Git commands already started finish and starts no more (they run up to four at a time); nothing is rolled back. Once clicked, the batch row reads Cancelling… (the header's Cancel for Pull all eligible reads Cancellation requested), and the status line then starts with the counts, for example Cancelled midway: 8 completed, 1 failed, 12 not started., until you start another action on any row or batch. Background checks skip a repository while an action is working on it and read it again as soon as it is done, so the row and What's Happening never disagree with what just happened.
