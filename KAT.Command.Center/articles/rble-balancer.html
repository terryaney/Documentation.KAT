RBLe Balancer

How each RBLe Balancer is spreading requests across its nodes right now: which nodes are healthy, how busy each one is, how fast it answers, and - if you are a balancer King - the controls to take nodes out of rotation, bring them back and replace their settings files.

What it shows

Every number comes from Sentinel. Command Center signs in to each balancer's Sentinel endpoint with your KAT Management credentials (Settings > Profile) and reads the balancer's status every few seconds. It never talks to a balancer or an RBLe node directly.

A balancer runs on every web server behind your load balancer. Command Center reads one web server's balancer at a time: the one chosen in the Host picker, which starts on the first host listed in Settings. Sentinel reads that web server's balancer directly, whichever web server handled the request.

The balancers are the ones you add under Settings > Sentinel · Balancer. They do not depend on the selected site, and switching sites changes nothing here. Status is read only while the Dashboard or this page is open.

The KPI tile

The Dashboard tile, titled RBLe Balancer · {Name}, shows one balancer at a time. With more than one configured, the dots and arrows along its footer switch between them; the tile never advances on its own. Clicking it opens this page on that balancer.

  • The header counts nodes by state. Every node out of rotation counts as Offline, whatever the reason.
  • Each node's row reads name · average response time, then CPU and memory meters, its share of traffic over the last 10 seconds, and its gate (see Capacity). Response time turns amber at 650ms and red at 800ms, everywhere it appears.
  • When a read fails, the tile says so and keeps the last reading it has, dimmed.

Reading the page

The header chips count nodes by state: Healthy, Unhealthy, Offline and Unknown. Click one to show only those nodes; click it again to show every node.

Below them, Balancer picks which balancer to show and Host which web server Command Center reads. Choosing another host starts its charts over from its next reading, and the Dashboard tile follows the same host. The choice lasts until the app restarts. The identity line names the balancer and its version, then the web server that answered and when, with the cluster on the right.

Banners

  • Unknown host (amber) - a web server that is not in the balancer's Hosts answered for the chosen host, usually because a name in Settings is not that web server's machine name. The page keeps working and shows that web server's numbers; it also joins the Host picker and every action's server list. Add it to the balancer in Settings, or dismiss the banner; dismissing also removes its What's Happening row until the app restarts.
  • Balancer settings not applied - the balancer rejected its own configuration and lists why.
  • Stale - the last read failed, so the page is showing older data.
  • Gate-aware routing is off - the cluster does not use the LoadAware policy, so nodes cannot be taken offline from here.

Charts

Response Time plots each node's average response, with the cluster's current request rate in its title. Traffic Share plots each node's share of requests, with a dashed line at an even share across the nodes that can take traffic. Each node keeps its colour for the session. Click a node's coloured balancer icon in the table to hide or show its line; a hidden node's icon turns grey.

Nodes

Each row shows the node, its state, its share of traffic, its capacity, CPU, memory, request rate, average response and total requests since the counts started. Click a node, or move to it with j / k, to see its details beside the list. In a narrow window the details open below the node instead: click it or press Enter.

Healthy
In rotation and passing its health checks.
Unhealthy
In rotation but failing an active or passive health check.
Unknown
In rotation, with no health result yet.
Draining
Taken offline. Requests already running finish; no new requests are sent.
Drained
Taken offline and no requests are running. Safe for maintenance.
App Offline
The node is serving its app_offline page, so the balancer sends it nothing. Bring online cannot change this; it returns when the app does.

Capacity

Each node reports how many requests it is running and queueing against its limits (Q: queued/max, with a pip per running slot). The balancer's gate uses that reading to decide whether a node can take another request. A node with no fresh reading is skipped by retries, and one with no reading at all is rejected.

Gate retries

When a node's gate is full, the balancer can resubmit the request to another node. The section under the table says whether retries are on and counts each outcome since the counts started on the chosen host.

King actions

Only a balancer King for that balancer's Sentinel endpoint sees the actions; everyone else gets a read-only page. Each one names the nodes, the cluster and the balancer it will change, and asks you to confirm. A node's menu opens from the … button at the start of its row (or press Space on the row).

  • Take Offline / Bring Online (a node's menu) and Take All Offline / Bring All Online (Take All) - stop or resume new requests to the nodes. Each comes in two forms: On the chosen host, or On All Hosts, whose confirmation warns how many nodes and hosts it changes. A node's menu offers the opposite of its state on the chosen host; its All Hosts items are always offered because other hosts may report a different state. A balancer with one host has no All Hosts form. Taking a node offline is offered only when the cluster uses gate-aware routing.
  • Reset Counts - start the traffic, retry and pick counts again, on the chosen host or on all hosts.

Nothing on the page changes until the next reading confirms it. If some servers fail, the dialog stays open and lists each one with what its failure means: a timeout may still have applied, while a denial or conflict changed nothing on that server.

Settings files

A balancer with a publishing node (Settings > Sentinel · Balancer) can read and replace its nodes' appsettings files. Without one these actions are unavailable.

  • View Settings (a node's menu) asks for a file name - appsettings.json by default - and downloads that node's file to your Downloads folder as {node}.{file name}. It then opens in Visual Studio Code when it is installed, otherwise in the app Windows uses for the file. If the file is already there you can replace it, save it somewhere else or cancel; with automatic opening off, a confirmation shows the saved path with Copy Path, Open Folder and Open File. These choices live under Settings > Sentinel · Balancer > View Settings Download. The node's file is never changed.
  • Update Settings (a node's menu) and Update All Settings (every node in the cluster) ask for a local appsettings*.json file, then confirm the deployment type, file name, size and nodes before replacing that file on each of them. The file must already exist on the nodes; it is overwritten whole.

A file you upload with Update Settings stays inside Command Center until it is sent. It is never shown, logged or saved.

When it refreshes

Each balancer is read every Poll Every seconds while the Dashboard or this page is showing; balancers on the same Sentinel endpoint share one read. ↻ and F5 read now. A failed read never raises a warning; the page and tile show it instead, and What's Happening lists a balancer that is stale, unreachable, denied, unhealthy or not applying its settings.
